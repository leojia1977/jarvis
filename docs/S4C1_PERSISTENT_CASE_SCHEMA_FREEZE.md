# S4-C-1 Persistent Case Schema Freeze

## Purpose
Freeze the durable stored-case schema before Sprint 4 adds any persistence API or status-mutation implementation.

`S4-C-1` does **not** implement storage yet.
It freezes:
- one durable case record shape
- one explicit lifecycle status model
- one first-class action-request schema
- one append-safe audit schema
- one frozen persistence backend choice for the pilot

## Frozen Backend Choice
Chosen backend:
- `sqlite_local`

Why this backend is frozen for Sprint 4:
- it keeps case data local to the controlled deployment boundary
- it avoids introducing a new external dependency before the pilot path is proven
- it supports deterministic retrieval, review-pack evidence, and audit-history persistence
- it is materially safer than reusing volatile session state such as Redis for durable analyst records

Explicit deferrals:
- no PostgreSQL or external database dependency in Sprint 4
- no Redis-only durable case store
- no ticketing-system or workflow-engine persistence

Config fields frozen in `backend/app/config.py`:
- `case_store_backend`
- `case_store_path`
- `case_store_retention_days`

## Stored Case Alignment Rules
1. The stored case must preserve the existing Sprint 3 `threat_case` shape as a first-class snapshot.
2. The stored case must also persist the Sprint 3 `case_view` projection so analyst reading order stays stable.
3. Persistence must not mutate the runtime `threat_case` schema.
4. Lifecycle state must be stored explicitly, not inferred from `verdict_status` or `investigation_status`.
5. Approval and action-request state must be stored as first-class records, not reconstructed from narrative text.

## Frozen Durable Record
Contract object:
- `PersistentCaseRecord`

Required fields:
- `schema_version`
- `case_view_schema_version`
- `storage_backend`
- `source_snapshot_id`
- `case_id`
- `threat_case_version`
- `lifecycle_status`
- `created_at_utc`
- `updated_at_utc`
- `review_owner`
- `threat_case`
- `case_view`
- `action_requests[]`
- `lifecycle_audit[]`

Schema notes:
- `threat_case` stores the governed runtime case as generated by the orchestrator
- `case_view` stores the analyst-facing projection from `build_case_view()`
- `action_requests[]` is present even when empty so approval work stays first-class
- `lifecycle_audit[]` is append-safe and records every durable state transition

## Lifecycle Status Model
Allowed durable case statuses:
- `open`
- `in_review`
- `approved`
- `closed`

Frozen transition matrix:
- `open -> in_review`
- `open -> closed`
- `in_review -> approved`
- `in_review -> closed`
- `in_review -> open`
- `approved -> closed`
- `approved -> in_review`
- `closed -> open`

Rules:
- `approved` means a human review decision accepted the current action direction or case disposition
- `closed` means analyst workflow is concluded; it does **not** imply destructive remediation executed
- any future expansion of statuses must update this matrix first, not add ad hoc string states in storage code

## Action Request Schema
Contract object:
- `CaseActionRequestRecord`

Required fields:
- `action_request_id`
- `status`
- `action_type`
- `targets[]`
- `requested_by`
- `requested_at_utc`
- `rationale`
- `approval_required`

Allowed action-request statuses:
- `draft`
- `pending_approval`
- `approved`
- `rejected`
- `cancelled`

Optional fields:
- `blast_summary`
- `source_case_status`
- `decision_by`
- `decision_at_utc`
- `decision_reason`

Rules:
- `S4-C-1` freezes the record shape only; it does not auto-create action requests
- runtime `suggested_action` may be converted into an action-request seed, but durable action approval remains `S4-C-3`
- no destructive execution is implied by any stored action-request status

## Audit Schema
Contract object:
- `CaseAuditEntry`

Required fields:
- `event_id`
- `event_type`
- `actor`
- `at_utc`
- `case_status`
- `reason`
- `details`

Allowed audit event types:
- `case_created`
- `status_changed`
- `action_request_created`
- `action_request_approved`
- `action_request_rejected`
- `case_closed`
- `case_reopened`

Rules:
- audit entries are append-only
- status changes must always create one audit entry
- approval decisions must always create one audit entry
- actor identity must be explicit even for system-generated events

## Alignment With Sprint 3 Contracts
`S4-C-1` must remain aligned with:
- `docs/SP3_B1_Case_View_Contract.md`
- `docs/SP3_B4_Degraded_UX_Contract.md`

Alignment rules:
- stored `case_view.executive_summary` must keep the same analyst-first reading order
- degraded cases must still suppress unsafe action enablement
- persisted lifecycle status is separate from `investigation_status`
- `investigation_status` remains a runtime analytical state; `lifecycle_status` is a durable workflow state

## Explicit Deferrals
Not in `S4-C-1`:
- actual persistence API
- retrieval endpoint implementation
- status mutation endpoint implementation
- action approval execution
- migration tooling
- full operator workflow UI

## Acceptance
`S4-C-1` is complete when:
- one durable case schema exists and is tested
- lifecycle statuses and transitions are explicit and frozen
- action-request and audit fields are first-class
- the persistence backend choice is frozen and justified against local sovereignty plus audit needs
- no persistence implementation has yet been coupled to unstated schema assumptions
