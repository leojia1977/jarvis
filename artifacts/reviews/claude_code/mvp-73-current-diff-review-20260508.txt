**N1 — Manifest self-referential SHA256 is stale (integrity gap, not a safety violation)**

`build_package()` at `scripts/build_private_deployment_package.py:291–309` writes the manifest three times:
- v1: templates only → SHA256 computed on v1 → appended as `package_manifest.json` file entry
- v2: file list now includes manifest entry → rewritten to disk
- v3: zip section appended → rewritten to disk again

The SHA256 stored in the manifest's own file entry (`af2a6de5…`) was computed on v1, but the file on disk is v3. The on-disk manifest does not hash to `af2a6de5…`. The zip also contains v2 of the manifest (before the zip section was added), so the zip's internal manifest differs from the disk manifest. This is inherent to single-pass self-referential manifest generation, but worth flagging for downstream consumers who may try to verify the manifest's own SHA256.
